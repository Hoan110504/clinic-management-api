🛡️ Authentication & Authorization

1. JWT Authentication (Access + Refresh Token)

Hệ thống sử dụng cặp token:

  • Access Token: JWT chứa {`{id, role}`}, expired sau 7 ngày. Gửi kèm mọi request trong header Authorization: Bearer <token>
  • Refresh Token: JWT chứa {`{id, type: 'refresh'}`}, expired sau 30 ngày. Lưu trong DB (bảng Users) để kiểm tra revoke.
  • Token Rotation: Khi refresh, cặp token mới được tạo và token cũ bị vô hiệu hóa (security best practice)

2. Password Security

  • Bcrypt hashing: Password được hash với bcrypt (salt rounds = 12) trước khi lưu DB
  • Không lưu plaintext: Không bao giờ lưu mật khẩu dạng text trong DB
  • Password policy: Tối thiểu 6 ký tự (có thể tăng lên 8+ trong production)
  • Must change password: Admin có thể force user đổi password lần đăng nhập tiếp theo

3. Role-Based Access Control (RBAC)

Mỗi route được bảo vệ bởi middleware authenticate và authorize([roles]):

router.get('/patients',
  authenticate,
  authorize([ROLES.ADMIN, ROLES.DOCTOR, ROLES.RECEPTIONIST]),
  patientController.getAll
);

→ Chỉ Admin, Bác sĩ, Tiếp tân mới xem được danh sách bệnh nhân

4. OTP Password Reset (2FA)

  • OTP qua Email/Telegram: Khi quên mật khẩu, user nhận OTP 6 chữ số
  • OTP Hash + Pepper: OTP được hash trước khi lưu DB, expired sau 10 phút
  • Rate limiting: Tối đa 5 yêu cầu OTP/giờ, 3 lần nhập sai OTP sẽ khóa
  • Reset Token: Sau verify OTP, nhận reset token (expired 15 phút) để đổi mật khẩu

⚠️ Xử lý Concurrency & Race Conditions

1. Tồn kho thuốc - Double spending

Vấn đề: 2 dược sĩ cùng lúc phát thuốc cho 2 bệnh nhân, thuốc chỉ còn 5 viên nhưng mỗi đơn cần 3 viên → tổng 6 viên (vượt tồn kho).

Giải pháp:

  • • Sử dụng Database Transaction với isolation level READ COMMITTED
  • • Sequelize: transaction.LOCK.UPDATE để lock row khi check tồn kho
  • • Atomic update: UPDATE Medicines SET quantity = quantity - :amount WHERE id = :id AND quantity >= :amount
  • • Nếu update affected rows = 0 → throw error "Thuốc không đủ tồn kho"

2. Đặt lịch hẹn - Time slot conflict

Vấn đề: 2 bệnh nhân cùng đặt lịch khám bác sĩ A lúc 14:00.

Giải pháp:

  • • Check UNIQUE constraint: (doctorId, appointmentDate, appointmentTime)
  • • Sequelize validation trước khi insert
  • • Bắt duplicate key error và trả message "Khung giờ đã được đặt"

3. Refresh token rotation - Token reuse

Vấn đề: Attacker lấy được refresh token cũ và dùng lại.

Giải pháp:

  • • Mỗi lần refresh, tạo cặp token MỚI và lưu vào DB
  • • Token cũ không dùng được nữa (so sánh với DB)
  • • Nếu phát hiện token cũ được dùng lại → khóa tất cả sessions của user đó (security breach)

Luồng Login:

  1. User gửi {phone/email, password} đến POST /api/auth/login
  2. Backend tìm user trong DB theo phone/email
  3. So sánh password với hash trong DB (bcrypt.compare)
  4. Nếu đúng, tạo 2 tokens:
    • Access Token: JWT chứa {id, role}, expired 7 ngày
    • Refresh Token: JWT chứa {id, type: 'refresh'}, expired 30 ngày
  5. Lưu refresh token vào DB (cột Users.refreshToken)
  6. Trả về client: {accessToken, refreshToken, user}
  7. Client lưu accessToken vào memory/localStorage, refreshToken vào httpOnly cookie (secure hơn)

Luồng sử dụng API:

  1. Mọi request gửi header: Authorization: Bearer <accessToken>
  2. Middleware authenticate verify JWT signature
  3. Nếu valid → extract {id, role} → gắn vào req.user
  4. Middleware authorize([roles]) check req.user.role có trong whitelist không

Tại sao cần 2 tokens?

❌ Nếu chỉ dùng 1 Access Token dài hạn (30 ngày):

  • Nếu access token bị đánh cắp (XSS, MITM) → attacker dùng được 30 ngày
  • Không thể revoke token (JWT stateless, không lưu DB)
  • User logout, nhưng token vẫn valid → security risk

✅ Với 2 tokens (Access ngắn + Refresh dài):

  • Access token ngắn hạn (7d): Nếu bị đánh cắp, chỉ dùng được tối đa 7 ngày
  • Refresh token lưu DB: Có thể revoke (xóa trong DB khi logout)
  • Token rotation: Mỗi lần refresh, tạo cặp token MỚI, token cũ vô hiệu
  • Logout thật sự: Xóa refreshToken trong DB → không refresh được nữa

Luồng Refresh Token:

  1. Khi access token hết hạn, client gọi POST /api/auth/refresh với {refreshToken}
  2. Backend verify refresh token signature
  3. Tìm user trong DB, so sánh refreshToken với DB (nếu khác → token đã bị revoke)
  4. Tạo cặp token MỚI, lưu refresh token mới vào DB
  5. Trả về {accessToken, refreshToken} mới

💡 Security bonus - Token Rotation:

Nếu phát hiện refresh token CŨ được dùng lại (attacker lấy được token) → xóa TẤT CẢ sessions của user → force re-login → ngăn chặn security breach.

✅ Giải pháp: Database Transaction với Row Locking 

// Sequelize Transaction
const t = await sequelize.transaction({
  isolationLevel: Transaction.ISOLATION_LEVELS.READ_COMMITTED
});

try {
  for (const item of prescriptionItems) {
    // LOCK ROW - chỉ 1 transaction được access row này
    const medicine = await Medicine.findByPk(item.medicineId, {
      lock: t.LOCK.UPDATE,  // Pessimistic locking
      transaction: t
    });

    // Check tồn kho
    if (medicine.quantity < item.quantity) {
      throw new Error(\`Thuốc \${medicine.name} không đủ tồn kho\`);
    }

    // Atomic update - dùng SQL để đảm bảo atomicity
    const [affectedRows] = await Medicine.update(
      { quantity: sequelize.literal(\`quantity - \${item.quantity}\`) },
      {
        where: {
          id: item.medicineId,
          quantity: { [Op.gte]: item.quantity }  // Double-check
        },
        transaction: t
      }
    );

    if (affectedRows === 0) {
      throw new Error('Concurrency conflict - tồn kho đã thay đổi');
    }

    // Log transaction
    await InventoryTransaction.create({
      medicineId: item.medicineId,
      type: 'out',
      quantity: -item.quantity,
      prescriptionId: prescription.id
    }, { transaction: t });
  }

  // Cập nhật status đơn thuốc
  await prescription.update({ 
    status: 'dispensed',
    dispensedAt: new Date()
  }, { transaction: t });

  await t.commit();  // Commit tất cả changes
  return { success: true };

} catch (error) {
  await t.rollback();  // Rollback về trạng thái ban đầu
  throw error;
}

Giải thích chi tiết:

  1. BEGIN TRANSACTION: Bắt đầu transaction, mọi thay đổi chưa được commit
  2. Row Locking (LOCK.UPDATE):
    • Transaction A lock row Paracetamol
    • Transaction B muốn lock cùng row → phải CHỜ A commit/rollback
    • → Đảm bảo chỉ 1 transaction được xử lý tại 1 thời điểm
  3. Atomic Update: quantity = quantity - X là atomic operation của SQL (không thể bị gián đoạn giữa chừng)
  4. WHERE condition: quantity >= X đảm bảo chỉ update khi đủ tồn kho
  5. Check affectedRows: Nếu = 0 → có transaction khác đã update trước → rollback
  6. COMMIT: Nếu tất cả OK, commit tất cả changes vào DB (atomic operation)
  7. ROLLBACK: Nếu có lỗi, quay về trạng thái ban đầu (không thay đổi gì)

💡 ACID Properties:

  • Atomicity: Tất cả operations thành công hoặc tất cả thất bại (không có trạng thái giữa chừng)
  • Consistency: DB luôn ở trạng thái hợp lệ (tồn kho không âm)
  • Isolation: Transactions không ảnh hưởng lẫn nhau (row locking)
  • Durability: Sau khi commit, dữ liệu được lưu vĩnh viễn (không mất khi server crash)

Hướng cải thiện (Production):

✅ Giải pháp High Availability:

  1. Database Replication:
    • SQL Server Always On Availability Groups (Primary + Secondary replicas)
    • Primary down → tự động failover sang Secondary (downtime < 30s)
    • Read queries có thể route sang Secondary để giảm tải Primary
  2. Load Balancer + Multiple API Servers:
    • Deploy 2-3 Node.js instances trên các servers khác nhau
    • Nginx/HAProxy làm load balancer phân tải requests
    • 1 instance down → load balancer tự động route sang instance khác
  3. Health Checks:
    • Endpoint GET /health check DB connection, Redis, AI API...
    • Load balancer ping health endpoint mỗi 10s
    • Unhealthy instance → remove khỏi pool
  4. Monitoring & Alerting:
    • Grafana + Prometheus monitor CPU, RAM, DB connections...
    • Alert qua email/SMS/Telegram khi có sự cố
  5. Backup & Recovery:
    • SQL Server automated backup mỗi ngày (full backup) + transaction log backup mỗi 15 phút
    • Backup lưu offsite (Azure Blob, AWS S3)
    • Test restore định kỳ (mỗi tháng) để đảm bảo backup hoạt động

Socket.io được dùng để cập nhật real-time cho:

// Backend - server.js
import { Server } from 'socket.io';
const io = new Server(httpServer, {
  cors: { origin: 'http://localhost:3000' }
});

// Authenticate socket connection
io.use((socket, next) => {
  const token = socket.handshake.auth.token;
  if (!token) return next(new Error('Unauthorized'));
  
  try {
    const decoded = jwt.verify(token, JWT_SECRET);
    socket.userId = decoded.id;
    socket.role = decoded.role;
    next();
  } catch (err) {
    next(new Error('Invalid token'));
  }
});

io.on('connection', (socket) => {
  console.log(\`User \${socket.userId} connected\`);
  
  // Join room theo role
  socket.join(\`role:\${socket.role}\`);
  
  socket.on('disconnect', () => {
    console.log(\`User \${socket.userId} disconnected\`);
  });
});

// Emit event khi có bệnh nhân check-in
export const notifyQueueUpdate = (appointment) => {
  io.to('role:doctor').emit('queue_updated', {
    type: 'new_patient',
    data: appointment
  });
};

// Frontend - useSocket.js

  auth: { token: localStorage.getItem('accessToken') }
});

  // Update UI

Socket.io vs HTTP Polling:

Tiêu chí Socket.io (WebSocket) HTTP Polling
Latency < 100ms (instant) Phụ thuộc polling interval (1-5s)
Server Load Thấp (persistent connection) Cao (nhiều requests lặp lại)
Battery (Mobile) Tiết kiệm Tốn pin (HTTP overhead)
Bidirectional ✅ Server push + Client send ❌ Chỉ client pull
Scalability ⚠️ Cần Redis adapter cho multi-server ✅ Stateless, dễ scale
Complexity Phức tạp hơn (connection management) Đơn giản (REST API)

Khi nào dùng gì?

✅ Dùng Socket.io khi:

  • Cần real-time (chat, notifications, live updates)
  • Latency < 1 giây là quan trọng
  • Data thay đổi thường xuyên (hàng đợi, dashboard)
  • Bidirectional communication (game, collaborative editing)

✅ Dùng HTTP Polling khi:

  • Data thay đổi ít (vài phút/giờ một lần)
  • Latency vài giây là chấp nhận được
  • Hệ thống đơn giản, không muốn quản lý WebSocket
  • Behind proxy/firewall không support WebSocket

⚠️ Scaling Socket.io với Redis:

Khi deploy multiple Node.js instances, cần Redis adapter để sync messages giữa các servers: 

import { createAdapter } from '@socket.io/redis-adapter';
import { createClient } from 'redis';

const pubClient = createClient({ url: 'redis://localhost:6379' });
const subClient = pubClient.duplicate();
io.adapter(createAdapter(pubClient, subClient));

import express from 'express';
import helmet from 'helmet';
import cors from 'cors';

// 2. CORS (trước body parser)

// 3. Logging (log mọi request)
app.use(morgan('combined'));

// 4. Body parsers (parse JSON/urlencoded)
app.use(express.json({ limit: '10mb' }));
app.use(express.urlencoded({ extended: true }));

// 5. Rate limiting (ngăn spam)

app.use('/api/medical-records', authenticate, authorize([ROLES.DOCTOR]), medicalRecordRoutes);

// 7. 404 handler (sau tất cả routes)
app.use((req, res) => {
  res.status(404).json({ success: false, message: 'Route not found' });
});

// 8. Error handler (PHẢI cuối cùng)
app.use(errorHandler);

Tại sao thứ tự quan trọng?

❌ Sai thứ tự - Ví dụ 1:

Nếu đặt app.use(errorHandler) TRƯỚC routes → errors không bắt được vì request đã đi qua error handler rồi mới đến route.

❌ Sai thứ tự - Ví dụ 2:

Nếu đặt rateLimiter SAU routes → attacker có thể spam requests mà không bị limit.

❌ Sai thứ tự - Ví dụ 3:

Nếu đặt express.json() SAU authenticate → req.body undefined trong middleware authenticate.

Middleware tự viết:

// middleware/auth.js
export const authenticate = async (req, res, next) => {
  try {
    const token = req.headers.authorization?.split(' ')[1];
    if (!token) throw new Error('No token');
    
    const decoded = jwt.verify(token, JWT_SECRET);
    req.user = await User.findByPk(decoded.id);  // Gắn user vào req
    next();  // Chuyển sang middleware tiếp theo
  } catch (error) {
    next(error);  // Chuyển error đến error handler
  }
};

export const authorize = (allowedRoles) => {
  return (req, res, next) => {
    if (!allowedRoles.includes(req.user.role)) {
      return next(new ForbiddenError('Access denied'));
    }
    next();
  };
};

Error handling middleware:

// middleware/errorHandler.js
export const errorHandler = (err, req, res, next) => {
  // Log error
  logger.error(err);
  
  // Custom errors (ValidationError, UnauthorizedError...)
  if (err.statusCode) {
    return res.status(err.statusCode).json({
      success: false,
      message: err.message,
      code: err.code,
      ...(process.env.NODE_ENV === 'development' && { stack: err.stack })
    });
  }
  
  // Sequelize errors
  if (err.name === 'SequelizeValidationError') {
    return res.status(400).json({
      success: false,
      message: 'Validation error',
      errors: err.errors.map(e => ({ field: e.path, message: e.message }))
    });
  }
  
  // Default 500
  res.status(500).json({
    success: false,
    message: 'Internal server error'
  });
};

💡 Best practices:

  • Security first: helmet, cors, rate limiting ở đầu
  • Body parsers trước routes: để req.body available
  • Error handler cuối cùng: catch tất cả errors
  • next() vs next(err): next() = tiếp tục, next(err) = skip đến error handler
  • Async middleware: dùng asyncHandler wrapper hoặc try-catch + next(err)

❌ SQL Injection attack:

Trả lời:

OTP Flow:

  1. User nhập phone/email → POST /api/auth/request-otp
  2. Backend: Generate OTP 6 chữ số → hash (bcrypt + pepper) → lưu DB với TTL 10 phút
  3. Gửi OTP qua Email (SMTP) hoặc Telegram Bot
  4. User nhập OTP → POST /api/auth/verify-otp → backend verify hash
  5. Nếu đúng: trả reset token (JWT expired 15 phút)
  6. User đổi password → POST /api/auth/reset-password với reset token
  7. Backend verify token → update password → xóa OTP record

Security: OTP hash (không lưu plaintext), rate limit (5 requests/giờ), max 3 lần nhập sai OTP.

Tại sao không dùng security questions? ❌ Câu hỏi bảo mật (tên thú cưng, trường cấp 2) dễ đoán, dễ tìm trên mạng xã hội. OTP an toàn hơn nhiều.

  (response) => response,
  async (error) => {
    const originalRequest = error.config;
    
    // Nếu 401 và chưa retry
    if (error.response?.status === 401 && !originalRequest._retry) {
      originalRequest._retry = true;

        const { data } = await axios.post('/api/auth/refresh-token', { refreshToken });

        return Promise.reject(refreshError);
      }
    }

  • Chuẩn quốc tế (WCAG) - thể hiện chuyên nghiệp
